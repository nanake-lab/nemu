# ADR 0043：交付线与本地模型研究线并行

交付线按时间推进可交付的 Nemu，研究线保留本地模型的长期探索。两线共用 Echo Core 的原则，各有任务，不拿研究何时成功作为交付日期的前提。

- 日期：2026-11-14（Australia/Perth）；任务：DESIGN-TWO-LINES-01。
- 状态：战略方向是用户已定；§3 三条边界为**候选（Claude 提出）**，用户合并本 ADR 即确认这三条边界。§4 的 U 项仍须逐项选择，合并不替用户填写答案。
- 范围：文档决策；[任务请求](../../tasks/requests/DESIGN-TWO-LINES-01.md)、[报告](../../reports/DESIGN-TWO-LINES-01/REPORT.md)、[差异登记](../traceability/diff-register.md) V2-174–177。

## 1. 先答黄金规则 17 三问

1. **能不能不加？** 不加分类系统、看板字段或新的运行机制。只加这一份 ADR 和 AGENTS 第 2 节的一段说明，让派卡的人知道哪些要按期交付、哪些可以继续探索；否则两种目标容易互相拖住。
2. **一个人会怎样？** 把有期限的工作做出来，同时留时间研究尚无答案的问题。共用设备时明确安排休息，结束再接续，不把被中断的思考写成一直在运行。
3. **加了以后，有什么从此改不掉？** 两线分工和首版范围可以由后续决策调整；已发生的经历和真实的睡眠记录不能重写。研究成果进入交付后可能涉及载体或规律迁移，因此沿既有审查、批准和迁移要求处理。本卡只记录安排。

## 2. 背景与用户决定

用户 2026-11-14 原话：

> 我们围绕经历模型 ECHO CORE 和 API 文字路线 + 本地常驻模型思维这条路线继续推进……同时我们不能丢掉本地研究模型这条路线。前者是我们可以推进交付的结果，后者是我们不要丢弃的研究方向。相当于一个公司内部的两个部门，一个负责交付，一个负责研究。交付受时间限制，研究则负责探索不赶进度。

| 路线 | 做什么 | 怎么看结果 |
| --- | --- | --- |
| **交付线** | 经历模型 Echo Core，加上文字路线（她说话走 API），加上本地常驻模型负责独处思考 | 按时间推进可交付的结果；完成范围与验收如实核对 |
| **研究线** | 本地模型研究，包括注入、Base 版、后训练带来的助手腔、权重学习等 | 探索问题，不赶进度，不承诺结果；失败与未定也如实留下 |

本地模型在两线中都存在：交付线负责把获批载体接成可用的独处思考，研究线探索它还可以怎样改进。“本地”不是划线标准，任务的目的才是。

## 3. 三条边界——候选（Claude 提出）

### a. 研究成果进入交付线

研究成果只能经 ADR、审查与用户批准，按迁移进入交付线。交付线不因研究未出结论而等待。交付自身所需的接线和验收仍须完成；本地思考所需的载体验证不能改名为研究后跳过。

### b. 共用一块 GPU

两线共用用户的一块 GPU。研究需要独占 GPU 时，她进入睡眠，明确记录睡眠与恢复，不悄悄停掉思考；存在时间与心情平复一律按 [ADR 0038 §3.2](0038-recall-affect-fading.md#32-两种时间淡化只读存在时间) 和既有规律处理，本 ADR 不改变它们。

GPU 测量仍按 AGENTS 第 9 节由用户安排安静窗口。

### c. 交付线第一版范围

第一版范围候选为：

- 核心打磨完成，并通过 MADE IN HEAVEN 验证。
- 按 ADR 0042 的文字路线说话（[PR #189](https://github.com/nanake-lab/nemu/pull/189)，未合并）。
- 本地模型负责独处思考，即 #189 的 U5 第一条路线“API 说话，本地 A 思考”，待用户在 #189 中选定。
- 能在桌面上与用户聊天。

这是交付范围候选，不是当前完成状态。MADE IN HEAVEN 沿既有实验谱系与验收要求，不在这里另定通过标准或宣称已经通过。声音、身体动作、上网交往是否进入第一版，交 §4 的 U 项。

## 4. 第一版还要用户选择什么

以下只问进入第一版还是后续交付，不替用户选择，也不把整个功能从项目目标中删除。

| 项 | 场景 | 放进第一版 | 留到后续 |
| --- | --- | --- | --- |
| U1 声音 | 你双手忙着，希望直接对她说话并听她回答 | 接通收音、识别、合成及相应体验验收 | 第一版先打字、读文字回复，声音另行交付 |
| U2 身体动作 | 聊天时希望她转向你、做动作回应，而不只是桌面上出现文字 | 明确首版动作范围，完成渲染、动作与交互验收 | 第一版以桌面聊天为交付体验，动作能力另行交付；不把这写成已符合完整身体标准 |
| U3 上网交往 | 你不在时，希望她以自己的身份在网上结识和回复别人 | 完成网络生活、权限及行动验收，并遵守诞生后启用的既有决定 | 第一版先与用户相处；涉及既定 v1.0/诞生范围的调整须由用户明确选择并登记 |

本 ADR 的“交付线第一版”不自动改写 ARCHITECTURE §2 的 v1.0 全部完成标准。若 U 项选择延期，具体受影响的要求与排期由后续文档承接用户决定；本卡不删验收。#189 的 U1–U6 在原 PR 内决定，本表编号只属于本 ADR。

## 6. 备选与后果

- **只做交付、放弃本地研究：** 无法保留用户明确要的长期方向，不采用。
- **等研究定论后再交付：** 把交付期限绑在未知结果上，不采用。
- **两线并行、成果经批准迁移：** 符合用户决定；保留探索空间，也承担单 GPU 的资源安排与睡眠接续成本。

派卡只在请求中写明所属路线，研究卡不得阻塞交付卡；不新增 cards.json 字段。研究结论不会自动进入她的正式生活。
