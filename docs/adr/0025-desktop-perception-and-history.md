# ADR 0025：桌面感知的读取范围、记入 H 与云端

- 状态：**草案，部分已由用户决定，部分待定**。用户 2026-10-25（Perth）对话中的决定记在第 3 节；第 4 节的问题用户要再想，不在本文替他定。合并由用户执行，合并即批准第 3 节。
- 日期：2026-10-25
- 范围：只记录决定和待定问题，不修改 `docs/CONTRACTS.md`、规格原文、代码或任务卡。需要的契约和代码改动见第 6 节，另开卡执行。
- 依据：v2.0 §1（H 只追加）、§2.2（可以重算）、§2.4（算子顺序）、§4 EV8、§5 LP5、§8（θ 的参考形式）、§18；CONTRACTS §4.1、§4.2、§5.2、§6；P6-08（PR #75）的实现与 ADR 0023。

## 1. 背景

P6-08 让她能感知桌面：窗口几何、前台应用的进程名、窗口标题、空闲、通知和勿扰状态、会议、锁屏。现行规则是：

- 标题读取属于 T1，默认拒绝，授权界面属于 P6-10（PR #75 的主入口不传授权，等同始终拒绝）；
- 进程名不需要授权；
- 低频语义事件经 `desktop.observation` 变成终端到核心的 `desktop` 观察事件（CONTRACTS §4.2），进入 H；高频几何只留在终端。

审视时发现三个问题：她能读到什么、读到的东西是否进入 H、能否交给云端模型，三者被同一个 T1 开关捆在一起；而 H 只追加、经历删不掉，进入 H 就是永久的。

## 2. 两类定义（用户认可）

讨论中区分了两类「定义」：

- **定义她：** 性格、什么对她重要、该记住什么。按第一性原理尽量不做，交给经历和规律。
- **定义她的感官：** 哪些信号能到达她、以什么颗粒到达。这一类无法不做，人的感官同样不是自己选的。它属于身体与终端的设计范围，可以也应该用实验谱系校准，而不是凭论证决定。

本 ADR 只处理第二类。

## 3. 决定（用户 2026-10-25 决定）

1. **不以「像人」为目标。** 她不是来模仿人的，精确是机器的能力。不采用「细节随时间淡化」：保持 H 只追加（v2.0 §1）与 LP5「时间本身不改变任何东西」，不为此改规格。
   - 不采用的理由：淡化后 (R, θ) 不能从 H 重算出原样（§2.2）；纠错记录和 L 引用的证据会失去对象；淡化的时间表本身也是预设规则。
2. **读取默认全开，包括窗口标题。** 用户可以在面板里按类别自行收窄，开关的界面属于 P6-10。
3. **标题随观察进入 H。** 不把「能读到」和「会记住」分成两个开关。
4. **云端说话模式可以携带标题。** 云端路线本质上是提示词路线；感知到的情境可以作为提示内容交给云端模型。
5. **敏感应用排除名单默认开启。** 名单内的窗口不读标题。初始类别：密码管理器、网银与支付、浏览器无痕/隐私窗口、系统凭据与登录对话框。具体名单和匹配方式由实现卡列出，用户可增删。

## 4. 待定（用户在想，不在本文决定）

1. **上报颗粒度。** 用户的方向：不应该丢掉「几点几分切到了哪个应用」。可选：
   - 逐次上报，每次前台切换一条事件；
   - 合并成片段再上报（例如「14:00–17:30 基本在 VS Code，中间切出去十几次」）；
   - 片段之外仍保留精确切换时刻的写法（形式待设计）。
2. **桌面事件是否算外源事件、进入 C（θ）。** 这一点与颗粒度共同决定对她的影响，见第 5 节。
3. **三层分法。** 几何只留终端；琐碎信号只用于当下门控与身体；少数转变进 H。用户持保留意见。
4. **排除名单内的窗口，进程名是否也不读。**

## 5. 为什么颗粒度不是中立的（推导，待实验核实）

按 v2.0 §8 的参考形式，θ 中事件的权重 ω_e = ρ_θ^{N_e}，N_e 是 e 之后的**外源事件个数**，不是经过的时间。若每次前台切换都算一个外源事件：

- 一天几百次切换会使真正的相处对基线 b 的影响在几天内被稀释；
- 这类事件的天性反应大概接近 0，σ̂ 变小，g = g₀·σ₀/σ̂ 升高，含义是「世界平静，小事也会触动她」。

前提「桌面事件算外源事件」规格没有写明，以上为按公式的推导，不是实测。另按 §2.4，每条被接受的记录都要经过 IRL、A、M（m = 0 下记录），逐次上报意味着逐次解释的成本。

**核实方式：** 交给 P5-30 的生活情景与耦合实验。同一段模拟生活分别按逐次上报与片段上报，并分别按「算外源事件」与「不算」运行，比较 θ（b、σ̂、g、λ）、R 与主动行为的轨迹。用户看结果后再定第 4 节第 1、2 项。

## 6. 后果与需要的后续改动

**后果（写明一次）：**

- 聊天等窗口的标题常含**他人的名字**，进入 H 后永久保留。「他人要求删除自己的数据」是 v2.0 §18 列出的未讨论问题，本文不解决。
- 云端模式下，标题会交给服务商处理，适用服务商的数据政策。

**需要另开卡的改动（本 PR 不做）：**

| 位置 | 改动 |
| --- | --- |
| `docs/CONTRACTS.md` §6、§4.1、§4.2 | 标题读取从「T1 授权后填写」改为默认允许、可由用户收窄；契约变更，按 ADR 0007 只增不改，交叉审查 |
| `packages/desktop-sense/`、`apps/desktop/src/sense/` | 默认读取标题；实现排除名单（默认开）；按类别的用户开关接口 |
| P6-10 面板 | 按类别的读取开关与排除名单的编辑界面 |
| CONTRACTS §5.2 模式 B 的投影 | 明确投影可以携带感知到的标题 |
| P5-30 | 第 5 节的对照实验 |

在这些改动合并前，PR #75 的现行行为（标题默认不读）保持不变，不受本 ADR 影响。

## 7. 备选方案

- **读取与记忆分开：** 标题默认可读但不进 H。用户否决（第 3 节第 3 条）。
- **细节随时间淡化：** 见第 3 节第 1 条，否决。
- **标题保持默认拒绝：** 现行做法。用户改为默认全开。
