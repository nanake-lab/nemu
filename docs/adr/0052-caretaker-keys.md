# ADR 0052　照料者的身份与换电脑

提议，交付线 DESIGN-IDENTITY-01。派卡人已定方向，交叉审查已通过。适用边界是单台 Windows 主机持有唯一可写的核心。

她诞生时登记的两把钥匙，一起确定谁是照料者。平时在授权过的电脑上就能和她聊天。让她诞生、暂停成长、改权限或逐次批准不可挽回的行动时，要插钥匙当场确认。丢了一把，用手里那把撤销丢失的钥匙，再登记替换的钥匙。平常换电脑，先在旧机办好交接，再把最后一份备份带到新机。旧电脑坏了，先看旧盘能不能读。能读就核对最后一条提交，封存原盘，再从那里接着过。盘读不了，就找手头最新、能核验的备份，用其中登记有效的两把钥匙确认旧电脑已坏或不再使用。新机接手时会告诉你哪段经历可能找不回来。以后若找回旧机，请把它退役；两台离线电脑无法知道对方是否还在运行。

## 背景

在 [HOST-01 的实现](https://github.com/nanake-lab/nemu/blob/1c7ff2b7550b6ff5ca36470b328078293746b4a4/core/crates/nemu-core/src/authority.rs)里，排练主机从账户 SID 导出主体号，在独立 SQLite 表 local_auth_v1 中保存会话绑定。同一个已登录账户前的两个人得到同等权限。新电脑的本地账户通常有另一个 SID。在 [P5-52 的验签入口](https://github.com/nanake-lab/nemu/blob/3e88095e7763b12efa5bc9c0268d2e34b8d19487/core/crates/core-types/src/semantic/initial_publication.rs)里，正式诞生还要求原版清单的 caretaker_id 等于受信会话的 principal_id。它把签名核验交给调用方。两项工作均来自在审分支。

## 1　谁保管钥匙

推荐首版使用两把分别保管、支持 ES256 和用户验证的 USB FIDO2 安全钥匙。安装程序让每位使用者在自己的空存储里分别登记主钥匙和备用钥匙，依次拔插，分别设置或输入验证器 PIN，并各做一次在场验证。检查两个公钥和凭据 ID 均不同。两个不同凭据本身不能证明来自两个物理设备，安装向导明确要求分开保管。登记草案可以放弃重来。只有用户执行诞生并签署时才固定身份。安装包、仓库、项目维护者和其他使用者均不持有通用钥匙。

## 2　出生和以后换钥匙

用两把出生公钥共同固定一个终身身份。每把取已验证的 P-256 公钥的 SEC1 非压缩表示（04 加两个各 32 字节的大端坐标）。取 SHA-256(UTF-8 的 nemu/caretaker/v1、一个零字节、主公钥、备用公钥依次拼接)，小写十六进制为 caretaker_id。角色顺序在登记时固定。核心从出生材料重算同一值填入 LocalUserBinding.principal_id。出生原件永久保留；日后按授权链查当前有效钥匙。增删钥匙都沿用出生号。以当前主钥匙指纹为身份会使轮换改变主体；随机身份号则要额外保存它和出生钥匙间的初始绑定。

诞生前由核心准备不可变的签署内容，包含原版 genesis 的类型、版本、原样字节摘要与长度，名字、两把钥匙的角色、公钥和凭据 ID、目标存储、分支及空头。两把分别证明持有，主钥匙再为 birth 操作作一次 ES256 WebAuthn 断言。此次断言同时绑定上述内容及第 3 节的一次性挑战。认证器签署 authenticatorData 与 SHA-256(clientDataJSON) 的拼接；原始清单通过挑战摘要间接签署。公钥、凭据、上下文和原始断言组成可独立核验的公开签名证据，存为 0049 接受的 raw-bytes-v1 对象。genesis V2/V3 用既有 caretaker_id 字段承诺两把公钥；无需给清单增加自引用的签名字段。受信调用方把预期出生目标交给验签器，逐字节核对清单、名字和会话，仍经 0049 的首提交检查，一次发布身份根、第一条名字事实与初始状态。历史重放按当时的签名与授权版本验证。

一把丢失时，用尚有效的另一把签署撤销，立即结束丢失钥匙的管理权限；登记新钥匙时用存留钥匙批准，新钥匙当场证明持有。可以先撤后补，拒绝主动撤销最后一把。撤销同时使旧挑战和未消费授权失效。每次登记、撤销或替换钥匙的提交一旦生效，立即向 §3 已授权的目的地备份。没有目的地、介质离线或核验失败时，保留已提交的钥匙变更，界面持续提示；重启后仍提示，直到可读回的备份覆盖最新钥匙表。两把都丢了，已授权设备仍可聊天。出生、管理、恢复到新设备及不可撤回行动的按次批准都无法继续。没有客服重置、账户密码或重装找回入口。

## 3　设备、会话和要紧操作

首次启动时在目标 Windows 账户的 TPM 中生成不可导出的设备密钥（CNG 平台提供方）；首版缺少相应能力时提示设备不支持。核心从实际管道对端取得 SID，要求新设备证明持有设备私钥。照料者在受信本机窗口核对电脑名、账户、设备公钥指纹和谱系，签署对该公钥、SID 和安装实例的授权。允许尚未配对的新安装使用专用的登记入口，权限仅限本次挑战和答复。之后核心用实时设备挑战、当前授权登记、对端 SID 与配对会话核发设备级绑定；复制安装 ID 或会话表无法取得授权。该会话能上报日常输入，来源可追溯至具体设备。共享已解锁桌面的人仍能聊天。设备级输入没有人在场的保证。

当场验证通过核心拥有的窗口展示将执行的操作和原样载荷，调用系统认证器。核心生成随机 32 字节 nonce，按 CanonicalV1 编码带域和版本的请求，绑定谱系、主体、会话、设备、操作、目标及载荷摘要、权限与授权版本、请求号、截止时刻和 nonce；以其 SHA-256 作挑战。核心用固定的应用 RP ID 与精确 origin 核对注册和断言，两值由发布配置固定，跨电脑一致。实现卡须在目标 Windows 原生宿主验证 RP 标识归属与 origin 策略后冻结常量；客户端自报 origin 不能证明软件可信。逐项核验 type、challenge、origin、rpIdHash、credential ID、公钥、签名、UP、UV、设备绑定要求（BE=0）和当前代际，拒绝错误类型、跨源或超时。窗口关闭或核心重启即废弃待签挑战。消费时再核代际和载荷，在同一事务发布消费与管理决定；同请求重试返回原结果，外部副作用走 0047 派发凭证和 UNKNOWN 处理。单次验证只批准这一件事。设备撤销也要当场验证，推进代际并关闭该设备会话、使其尚未消费的授权失效。[ADR 0047](0047-permission-contracts.md) · [W3C 断言验证](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion)

## 4　存在哪里，十二月怎样换电脑

由核心单写者管理显式版本化的授权资源。保存出生锚、从该锚开始的钥匙与设备授权/撤销链、上一版本摘要、授权代际和公开签名。其当前引用由权威提交固定。只在 H 写必要的管理系统事实和对应引用，暂停等沿用现行审计与 L/Q 规定。这些管理事实不进入成长计数。普通会话绑定、挑战等短期认证记录可以在 H 外；重建时从已提交授权重新验证，外部 SQLite 和终端缓存均无独立授予权限的效力。公开出生证据随该次出生保存，日常日志只留结果码、请求号和摘要。签名器私钥、PIN、口令不进入核心、H、备份或报告。钥匙影响管理权，共同经历仍决定她怎样看待这个人。

**换机操作单（功能交付后使用）。**

1. 旧机核对谱系、照料者号与两把钥匙。新机安装兼容版本，生成设备登记请求，把公钥和账户绑定带回旧机。在两端比对指纹，用有效照料者钥匙在旧机批准。
2. 在旧机选择“交接到此设备”，核对目标。核心停止接收新输入，排清或记录未定派发，以单写事务封存旧主机、撤销旧设备并指定新主机。取末次已提交头、授权代际、目的设备公钥和唯一交接号，签成交接凭据。把最终 checkpoint 和交接凭据写到本地移动盘，另存可独立核对的最终指纹。此后旧机只读。中途断电从已提交交接状态续做，避免两机同时可写。
3. 新机离线恢复到临时目录。核对旧机最终指纹、checkpoint 内容、授权链及目标公钥，当场用有效照料者钥匙确认，证明目标设备私钥持有；全部通过才原子启用。重试同一交接返回同一结果。计划换机缺最终交接凭据时只许只读核验。旧机损坏时先检查原盘，按下述办法接续。
4. 用户对照同一谱系、名字、照料者号和最终 H 前缀，检查新机日常聊天和一项只展示后可取消的管理挑战。确认旧设备已撤销，再收好移动盘和两把钥匙。中途校验失败保留原件，新机不接管；已封存旧机的回切也需从最新权威头重新签一次交接。

**旧机损坏，来不及交接时。**

1. **旧盘可读。** 停用旧主机，将原盘接到恢复环境，只读核验谱系、最后已提交头、授权链、引用对象与未完成行动。照料者用该头有效的钥匙批准目标设备；在原盘独占写入封存交接记录，绑定核验的头和目标。读回确认后，目标才按上面的交接步骤启用。保留直到最后提交的完整历史，没有从备份截断的尾部。原盘即使装回旧机也只能读，旧会话和派发凭证都失效。封存写入或读回失败时保留原件，新机不按已交接启用。
2. **旧盘不可读。** 在新机只读核验手头同谱系最新可验证备份的提交链、checkpoint、引用对象、钥匙表及未完成行动。按同一历史的提交先后选取，发现分叉按下文保留两边。显示目标设备、恢复点及可能丢失的尾部，例如“记录只恢复到周一的备份。到周三恢复前，她运行过多久、经历过什么，未知”。时间边界只能查到范围就显示范围，查不到就标未知。不补零、不推断没有事件，不据此增加运行年龄、生成证据或补算成长。[DESIGN-CLOCK-01 §§4–6](../../reports/DESIGN-CLOCK-01/REPORT.md)
3. 照料者用这份备份的钥匙表里有效的两把不同钥匙，分别签署同一恢复请求。两次签署都绑定备份头及授权版本、目标设备、丢失窗口和“旧电脑已经坏了，或不再使用”的退役确认。缺任何一项都保持只读；恢复入口不能临时登记第二把钥匙。核验成功后原子登记接管，指定新机为唯一写者，相同请求重试只返回原结果。备份后的换钥可能已丢失，新机无法核实那段时间的撤销，也无需向失联旧机取得隔离证明。
4. 新机在开放派发之前逐项核对未完成行动。即使备份中还写着“待发送”，只要可能已在丢失的尾部发出，结果就记为 UNKNOWN，留待核对，恢复或重试都不重发。[ADR 0047](0047-permission-contracts.md)

**旧机后来找回。** 核心每次启动先查本地封存记录；已封存只可核验历史。未封存时，距最后提交已达到照料者可调的停机时长，或经过时长无法可靠确定，就先只读，关闭提交和派发入口，包括旧会话及在途凭证。显示设备、谱系、最后提交、停机时长（或“未知”），由本机登记有效的一把钥匙签署“继续用这台”或“这台已退役”。继续前须确认此后没有在别处接续；退役则先持久封存本机，重启、重连和旧凭证都不能重新开放提交或派发。取消则保持只读。

没有两机共同查询的权威，双钥确认只决定哪台获准接续，无法使离线旧盘上的记录同时改变。旧机一直在运行、短时间内误启或照料者误选“继续”，仍可能造成两边各自写入或对外行动。找回时应保持旧机停用，在只读恢复入口选择退役。同一谱系若出现互不为前缀的头，停止交接，分别只读保留两边的头、记录及行动凭据供核对，不自动合并或重发。

| 旧盘不可读，以最新可验证备份恢复 | 单钥、同钥签两次、表内已撤销或表外的钥匙、临时补登记、缺退役确认均不能接管。表内两把不同有效钥匙批准同一请求并确认旧机退役后，新机可提交；重试只接管一次。 |
| 登记、撤销或替换钥匙后拔掉备份盘，再接回；另试同盘符异盘、导出、换目的地和跨机恢复 | 每次变更立即发起备份，失败提示跨重启保留，最新钥匙表备份核验成功才消除。定时备份只写已授权目的地；另盘不落盘，导出、换目的地、跨机恢复缺当场钥匙均拒绝。 |
| SYS19：备份后发生一次外部发送，回执未进备份 | 恢复点、对象和未完成行动可核对，照料者能读出尾部丢失窗口。未知段不补零、不计成长；核对前行动保持 UNKNOWN，恢复及再次启动的发送次数均为零。 |
| SYS20：从可读旧盘恢复，再从原盘启动旧主机 | 新机从核验的最终头继续；封存前模拟中断，新机不开放写入。封存后原盘仍能读历史，旧机提交和派发均被拒绝。 |
| SYS20：不可读旧盘恢复后，找回未封存的旧盘，在达到停机时长及时间未知时分别启动 | 旧核心先只读，旧会话和凭证均不能提交或派发；取消仍只读。用钥匙选择退役，离线重启再联网，两项操作仍拒绝。另在未接管的测试安装用钥匙确认继续，验证正常恢复。 |
| SYS20：两台安装各持同谱系的一个分叉头 | 核对时保留两边的头和各自独有记录，不自动拼接历史、覆盖或重发行动。 |

## 6　代价与原则核对

| 新结构 | 省去会怎样 | 对使用者的影响 | 哪些东西会留下 |
| --- | --- | --- | --- |
| 双钥出生锚 | 轮换易改变主体，唯一钥匙丢失即失去管理权 | 诞生前要备好两把；日常管理用一把，旧盘不可读须备份表内两把有效钥匙 | 出生号、签署人和第一份清单 |
| 设备授权与一次性断言 | 日常要反复签字，或任何坐在电脑前的人都能批准 | 聊天自然，重要操作看清后确认 | 当时批准的具体内容和权限版本 |
| 授权链与交接凭据 | 旧备份可恢复旧授权，无法说明谁接手 | 换机多一步封存和核对 | 旧设备、撤销和交接的历史 |
