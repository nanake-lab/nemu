# DESIGN-IDENTITY-01　照料者身份设计（交付线，重档）

平常换电脑时，由旧机封存最后的记录。旧机突然损坏时，两把仍有效的钥匙可以批准从手头最新的备份接续；旧机失去写入和派发能力后，新机才接手。

推荐在诞生时分别登记两把 USB 安全钥匙，日常聊天只用已授权电脑。

请用户在交叉审查后决定是否采用这份设计；换机步骤要等实现卡通过验收后才能使用。

## 决定与理由

| 自行提出的决定 | 理由和替代方案 |
| --- | --- |
| 两把独立 USB 安全钥匙，各自支持本人验证 | 同机 Hello 可能随电脑一起丢失；手机混合传输受系统和提供方影响；软件文件需要自己管理可复制秘密。云端托管恢复会增加另一名授权方。使用不同设备比同一设备内的两个凭据更能抵御整机损坏。 |
| 出生号取有序双公钥摘要，之后靠连续授权换钥匙 | 备用钥匙也在出生时获得承诺；轮换无须改写 genesis、H 或过去的身份绑定。失去全部钥匙后，原已授权设备仍能聊天。 |
| 硬件 ES256 断言绑定清单、名字和目标 | 0049 接收原版清单与签名证据；普通 WebAuthn 验证器能签挑战，无法给任意文件直接作裸签名。 |
| 授权链保存在核心提交引用的版本化资源，短期会话可在 H 外 | 全放进 H 会混入大量连接记录。只放侧表又无法随提交验证撤销、备份和恢复。 |
| 日常操作凭设备，按次管理凭照料者钥匙 | 同账户前的另一个人仍能聊天；无法借同一连接批准管理操作。保留 0047 的不可挽回桌面三档及 T3 逐项批准。 |
| 计划换机先授权、封存，再移交一个可写头 | 单机离线环境无法只凭旧备份判定最新撤销状态。新机以交接凭据指定的最终头为准。 |
| 灾难恢复须双钥确认恢复点和可能丢失的尾部，接管前核实旧机已经隔离 | 一把遗失的钥匙不足以批准有损恢复；双钥能批准接续，旧机在脱网时能否继续写入或行动还要单独验证。 |
| 三种语言只通过专用入口接收用户答复，沿用现有清单与会话消息 | 生成器继续支持旧标签，上传入口无法借有效摘要创建授权。按契约、核心、终端、排练迁移交付，各自验收见 ADR §5。 |

## 规格对照与核验

| 依据 | 设计位置 | 实现卡应提供的证据 |
| --- | --- | --- |
| v2.0 §§5.4、16，0047；AC2-18、AC2-20 | ADR §3 | 管理绑定到会话、报警和版本；拒签与重放均不改状态，恢复后按原规律补算。 |
| v2.0 §§10、13，草案 0049；I18、I29 | ADR §§2–4 | 从原始 genesis 和公开材料重算主体，修改名字、清单或目标均拒签；只用临时谱系做迁移验收。 |
| ADR 0039 P3、P7、P9；I02、I16 | ADR §§3–6 | 单写事务及离线验签。旧设备撤销后失去会话，历史仍可核验，认证旁表无法改变权威状态。 |
| 0047、SYS17、SYS21 | ADR §§4–5 | 迁移故障回退、在两台测试安装间交接；三端拒绝伪造的首块与完整权威对象。 |
| SYS19、DESIGN-CLOCK-01、0047 | ADR §§4–5 | 单钥拒绝、双钥成功；核对备份对象、未完成行动及用户能读懂的丢失窗口。未知不算零、证据或成长，可能发过的行动不重发。 |
| SYS20 | ADR §§4–5 | 旧机尚可脱网写入时，新机不能接管。隔离后，新机继续写，旧机离线重启及归来均不能写入或派发，分叉不自动合并。 |

核对了 #258 的 LocalAuthority::open / binding 和 #260 的 verify_birth_material、BirthNameRecord 及签名证据类型。Windows 接口与认证器签名格式依据见 [ADR §1–3](../../docs/adr/0052-caretaker-keys.md)。开 PR 前核对了 main 和在审 PR 的占号；交付时 #264 已合并到 5e365860，#260、#262 分别占 0049、0050，主线已含 0051 与 V2-193。本卡追加 0052 和 V2-194。
