## 2. 怎么放

按用户要求改为 **固定协议 → 已保留的对话 → 本轮来由 → 最新输入 o**。先对基础对话、o 和必要事实补齐引用/更正，再以剩余空间接纳完整来源包；首个包超预算即停。全局正文去重位置为 o 优先、其次 D、最后 E；完整原文与已投递片段分别绑定。

ADR §2.3 保留正文引用、目标更新、别名合并、更正超预算四例及已通过复审的长对话例：整条接续链已超窗，D 只保留最近两条、o 固定；在没有额外正文依赖或可选包且基础请求能装下的条件下，唯一原文集合只有 D 的两条与 o，E为空、K=0。保留直接接续引用，较早祖先正文不回填。这个条数是例子的既定对话计划，不是新参数。

容量失败的恢复须以 r4 和实际 D 新绑定，完整计量后能放下；若固定 o/必要事实确实依赖旧原文或更正，它们仍要加入。固定必要材料已超窗时缩小 D 无效，须有足够的已获准容量等实际条件改变再重组。§2.4 继续绑定实际 o、D、每次查询及其参数/可取回结果、关系类别/映射版本及直接接续引用；哈希只作核验。

后置来由可保留更长的共同前缀，但删除上轮来由后新进入干净对话前缀的部分仍需处理。两轮 `P,D,E1,o1` → `P,D,o1,a1,E2,o2` 的共同前缀只保证到 D；这里是依据官方前缀缓存规则的设计推导，不是测量。缓存不参与选材，资源或来源变化时接受重建代价。出处：[OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching)、[Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。

## 3. 放不下或失败怎么办

| 场景 | 设计规则中的结果 |
| --- | --- |
| 可选来由首包太长 | 停止选包，仍可发送完整可用的基础请求；不跳去选后面的短包 |
| 对话已含旧话，但其更正放不下 | 本次请求不发送；另行改变对话范围须新绑定、从完整闭包重新开始 |
| 长接续链已超窗，D 裁短、o 固定 | 接续祖先不回填 E；新的完整必要材料能放下才恢复。若 o 等固定材料的真实正文依赖仍超窗，缩 D 无效，必要更正不能删 |
| 分解未知与可恢复槽并存，或包关系/原文无法完整取得 | 整个投影不可得，本模式不发送该请求；不把部分集合当作全局最重 |
| U6 解释仍在排队或积压 | 继续等待本轮及其有序依赖，不因等待时长结束本轮；实际过载、取消或依赖失效仍按已有生命周期处理并如实显示 |
| U6 解释失败 | 本轮不生成或投递她的回复，运行界面如实显示故障；恢复或重试后的解释影响后续状态，不补发已失败的本轮回复 |
| 无合格经历、但所有依赖完整可知 | 新增经历为空，保留真实诞生事实/环境和当前对话；是正常空包，不等于中性 |

既有失败情形与长接续链仍列在 ADR §3.2。本轮把 U6 的不设等待时长、解释失败无角色回复、故障显示与晚到解释不补发写入后继验收；实际等待与故障显示仍须测量，测量值不变成等待上限。全部为后继要求 **not_run**。
