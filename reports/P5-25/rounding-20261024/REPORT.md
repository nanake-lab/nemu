# σ 1 ULP：逐步舍入定位，尚未修复

## 结论

环境仍在；按用户2026-10-24指示只检查此次数值差异。main仍为`0b5412e`，PR #77仍为`081e48f`且无新增审查意见。原实现、验收断言、原Python脚本、固定输入及失败日志全部不变。

**不能把现有差异归因于 Rust 括号、累加顺序或 sqrt 错误。** 首个σ差异的前态逐位相同，第一处不同是残差平方：原Python `residual ** 2`调用平台`pow`，Rust执行显式乘法。用整数商余数对输入的精确有理平方做最近偶数舍入，证明该输入应取Rust结果；Python的pow结果并非最近可表示值。因此，仅要求Rust按ADR0019 §8逐次最近偶数舍入，不能同时让它复刻这一不可变的Python平台pow结果。

本轮没有选择平台pow仿真、没有改变oracle、没有放宽断言，也没有把“定位完成”写成“修复通过”。需要用户明确是否允许新增固定运算次序的Python参考，再按同样严格的位比较核验；原参考与失败证据保留。

## 逐步证据

原数据500组/72,822事件全部重新读取，仅做诊断，不重跑或改写原验收。37个外源事件的`x**2`和`x*x`位模式不同；这37个输入的整数精确舍入均支持乘法，pow均相差到邻值。13个事件最终传播为σ位差。最早平方差异在第19组第149事件（从1计数）；最早σ差异在第59组第147事件。

首个σ差异的21个步骤全部列于`trace.json`；以下是传播链：

| 步骤 | 原Python参考 | Rust显式顺序 |
| --- | --- | --- |
| 事件前weight / reaction_sum / square_sum / b | 四项逐位相同 | 四项逐位相同 |
| `residual = a-b_before` | −1.3272604063944256 | −1.3272604063944256 |
| 残差平方（首次分叉） | 1.7616201863822958，`3ffc2f98a607c423` | 1.7616201863822956，`3ffc2f98a607c422` |
| `rho*old_square_sum` | 5.009915739404429 | 5.009915739404429 |
| 上项 + 残差平方 | 6.771535925786725 | 6.771535925786724 |
| `n_sigma*(sigma0*sigma0)` | 1.6356283774832754 | 1.6356283774832754 |
| 方差分子 | 8.407164303270001 | 8.40716430327 |
| 方差分母 | 31.77596609900536 | 31.77596609900536 |
| 方差 | 0.26457619815792666 | 0.2645761981579266 |
| sqrt后的σ | 0.5143697096038283 | 0.5143697096038282 |
| `0.3/σ` | 0.5832380764237894 | 0.5832380764237896 |

b分子、分母、权重递推、反应和、先验σ平方和g的分子均无差异。Rust先计算weight、Python先计算square_sum，但这两项只读取各自的旧状态，没有相互依赖；改变其先后不能修复已经存在的平方位差。两边都先加平方项到已单独舍入的衰减平方和，再加先验、除分母、开方、算增益。

`trace.rs`直接引入生产`numeric.rs`及既有`libm 0.2.16`，在debug与优化构建分别打印步骤。两次均与显式顺序的21项位模式完全相符。把**同一个**方差输入分别送入Python `math.sqrt`及Rust `libm::sqrt`，两个不同方差各自都得到相同σ，排除sqrt函数或sqrt前后移项作为首因。见`rust-debug.tsv`、`rust-release.tsv`、`verification.json`。

## 为什么没有提交powf“修复”

同一Rust 1.99.0、同一输入，probe明确使用`-C target-feature=-fma`：

| 运算 | opt-level=0 | opt-level=3 |
| --- | --- | --- |
| `x*x` | `...c422` | `...c422` |
| 固定版本`libm::pow(x,2.0)` | `...c422` | `...c422` |
| `x.powf(2.0)` | `...c423` | `...c422` |
| `x.powf(black_box(2.0))` | `...c423` | `...c423` |

常量powf在debug碰巧匹配，优化后不匹配，因此不能拿它冒充跨构建的修复。运行时指数只是诊断对照，不进入生产：它依赖平台数学库，且刻意保留的是这里不满足最近舍入的pow结果；当前编译选项也不能约束外部动态库的内部实现。没有引入这种依赖或使用black_box阻止优化来通过验收。

CPython3.12.14的`float_pow`源码在特殊值处理后调用`ix = pow(iv, iw)`；本环境Python3.12.14 / glibc2.39。已有Rust `libm 0.2.16`源码对指数2直接`return x*x`。来源与源码哈希见`sources.json`，实验原输出保留。
