# P5-34 W02 上传恢复

## 授权与范围

2026-10-27 用户要求“换个稳定的方式就算遇到网络波动也能上传过去”。据此只修改 `.github/workflows/windows.yml` 的 W02 上传部分；原测试命令、检查名称、路径判定、可信来源限制、60 分钟作业时限和最终 Windows 汇总门禁均保留。本次不再修改 core-store 或契约源码。

## 原失败

提交 c6525e65 的 Windows run 40456116456：W02 35 项测试和 2 项文档测试通过，新增 WAL 回归也通过。上传三份日志时，06:09:39 UTC 开始向制品服务传输，06:14:39 报 `Upload progress stalled`，最终作业失败。06:18:23 后到的 `Uploaded bytes 4725` 不撤销 failure。完整证据位于 `verification/review-20261027/final-ci-c6525e65/`。

## 修改

- 仍使用已固定提交的官方 upload-artifact v4，不新增上传依赖或更改凭据。
- 最多三次上传尝试，各自上限 6 分钟；重试前分别等待 20、40 秒。此上限只约束上传步骤，测试和作业时限没有改动。
- 每次复用当前 run 的同一份日志，不重新运行 W02。第二、三次附件名分别加 `-retry-2`、`-retry-3`，避免半上传附件名称冲突，也不删除前一次附件。
- 一旦成功，后续重试跳过；取消作业时不继续重试。
- 只有上传步骤临时允许继续，最后的 `Require W02 evidence upload` 必须确认至少一次 `outcome=success` 且返回有效 artifact ID，否则抛错。全部上传失败、全部跳过、未知状态、失败却残留 ID、成功却缺少 ID，均不能通过门禁。
- 原 W02 测试失败仍会使作业失败，上传重试不会清除它。缺少日志仍按 `if-no-files-found: error` 处理。

网络持续不可用时，有限次重试仍可能失败；届时保留本地日志和失败状态，不伪造上传成功。该实现用于从短暂传输失败恢复，不改变验收含义。
