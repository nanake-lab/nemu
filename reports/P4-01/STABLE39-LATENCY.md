## 时间花在哪里：能确认的部分与不能识别的部分

旧 trace 保存的事件终点是 VoiceRuntime.publish 构造的 event.ts，时间采样在 schema.parse 和 emit 之前；不是回调收包时间，更不包含 utility → 主进程 → 舞台的完整 IPC 或物理麦克风路径。因此“事件发送耗时”不在这份旧日志里，不能填成 0。

| 部分 | 现有证据 | 能否单独量化 |
| --- | --- | --- |
| 持续语音门限 | SenseVoiceProvider 中独立 bargeVad 的 minSpeechDuration=0.2 秒，现配置固定 | 配置为 200 ms；旧 trace 未记录原生门限计时起点，不能宣称实测正好占 200 ms |
| 起音检测与窗口等待 | 正常 VAD speechStart 相对参考起点：中位 100.11、p95 995.04、范围 −179.21…1120.91 ms | 可观察这个混合区间，但正常 VAD 与 bargeVad 是两套状态，且正常 VAD 自身有 32 ms 配置；不能把该区间全叫作 bargeVad 推理耗时 |
| 正常 VAD 起点事件 → 打断事件 | 中位 198.50、p95 201.58、范围 177.55…201.95 ms | 两个已记录事件之间的实测差；与上行逐条相加等于总打断延迟，但包含门限差、窗口/包相位、处理和参考偏差，不能再次叠加 200 ms |
| 原生 VAD 推理 CPU 耗时 | 没有 acceptWaveform 前后独立时标 | 未采集，JSON 为 null |
| JS 处理/排队/调度 | 20 ms PCM 输入；逐条有最大迟包值，最大值不是触发包自身的迟包 | 未采集独立区间，JSON 为 null；不得用全段最大迟包当作该次触发的实际耗时 |
| 事件 ID/封装、schema 校验、发送与接收 | publish 的时间采样位置可从源代码确认，无各步耗时打点 | 未采集，JSON 为 null；部分发生在 event.ts 之后，不能从两个事件时间倒推 |
| VAD 结束静音等待 | 正常 vad minSilenceDuration=0.2 秒 | 200 ms 配置；总结束延迟中位 319.80 ms，减去配置的 119.80 ms 仅为混合残差，不是某一独立阶段 |

按配置相减，总打断中位 300.30−200=100.30 ms，也只是残差，不是已测得的“额外处理时间”。各区间的中位数不能直接相加来复原总中位数。没有足够证据给出 VAD、处理、发送各自可靠的百分比。

正式重测如需拆分，可增加不改变判定的测量打点：每个 feed 的包到达/进入/返回、两次原生 acceptWaveform 前后、barge hook、publish 进入、event.ts、schema 校验完成、emit 回调接收。必须把新增打点的开销和 event.ts / 实际接收两个终点分别说明。原生内部的后验变正与 200 ms 起算点仍不可从 Node 当前 API 精确读取，不应装成已有独立测量。此轮没有为补这些打点而运行新的测量。

## 提前触发及可疑样本：逐条说明证据边界

按“早于参考点，延迟 <0”定义：打断 0 条、VAD 结束 0 条。正常 VAD 起点早于参考 1 条；另有 1 条打断小于名义 200 ms。不能把正常 VAD 起点事件误写成 voice.bargeIn 提前。

| 样本 | 现象 | 能确认的原因或不能确认的原因 |
| --- | --- | --- |
| user-ja-014 | 正常 speechStart=2020.787，参考起点=2200.000，早 179.213 ms；bargeIn=2220.125，相对参考仅 20.125 ms；speechStart→bargeIn=199.338 ms | 两个系统事件的间隔接近名义持续门限，现有数据不支持“系统只等了 20 ms 就触发”。可能是自动参考偏晚，也可能是前置噪声/语音检测提前；旧 trace 没有音素真值或后验，不能唯一归因。两锚一致也可能共同偏差，人工抽检只验证抽中的五条，不擅自扩充或重抽。 |

另外五条 ≥1000 ms 的打断为 user-zh-002、007、009、012、017。它们的主锚起点都约为 980 ms，落在固定首部 1000 ms 数字补零区间内、距补零边界约 20 ms；这是已知输入构造与参考点的关系，不是新的能量阈值检测。该点不能当作精确的“第一个能听到的音”。80 ms 网格可能解释边界附近的小偏移，但不能据此解释或校正整段约 1 秒差异。

这五条正常 VAD 起点到打断事件仅约 180–199 ms，而“参考起点→正常 VAD 事件”约 960–1121 ms。故长尾集中在前一个混合区间；是否由起音检测本身还是共同偏差的参考导致，需要人工质量检查，不能全归咎于推理或发送，也不能静默把点移到接近系统检测的位置。当前仍照用户方案保留这五条及数值，随机抽检集合不变。

## 250 ms 预算与 N0 决定

32 ms 原生窗口（512 / 16000）与 20 ms 输入包都占预算。仅将 200 ms 持续量按整窗计数，ceil(200/32)×32=224 ms，再计最多一包 20 ms 已约 244 ms；这只是量级预算，不是当前实现的严格延迟上界或阶段实测。初始窗口、原生起点确认、声音到后验变正的时间和处理/发送仍在外面。原生首次正窗及后续样本计数还会改变相位关系，不能承诺固定“还剩10 ms”，也不能简单重复加上两个互相重叠的窗口。

可选方案、代价和需要决定的事项另见 N0-P0-09-LATENCY-OPTIONS.md。没有修改门限或模型；39条结果只供 N0 / P0-09 讨论。人工标注、抽检处理和安静窗口全60重测完成前，不转可审查。
