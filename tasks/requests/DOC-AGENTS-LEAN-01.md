## 要改的（按下面的新文字改，可以调整措辞让上下文通顺，但意思不能变）

### 1. §2「认领」后面追加一段「PR 拆小」

> **PR 拆小：** 一张卡可以分成多个 PR，每个 PR 只做一件能单独验证的事，代码改动尽量控制在几百行以内（自动生成的文件不计）。标题写成 `<类型>(<任务号> <n>/<m>): <标题>`，例如 `feat(P5-14 2/4): outbox 原子登记`；只有一个 PR 的卡照旧写 `<类型>(<任务号>): <标题>`。第一个草稿 PR 就是认领标记。最后一个 PR（n = m）合并后，这张卡才算完成。拆分计划写在第一个 PR 的描述里，后面可以调整，但要在 PR 里说明。

### 2. §2「工作区」整段替换

> **工作区：** 每个并行会话固定占用一个工作区 `D:\Dev\nemu-wt\<槽名>`，槽名用执行者加序号，例如 `codex-a`、`codex-b`、`gemini-a`。开新卡时，在自己的工作区里 `git fetch origin` 后从 `origin/main` 切新分支，不再为每张卡新建工作区。切换前确认没有未推送的提交、没有未提交的改动；有的话先推送，或者停下来问。虚拟环境、缓存、模型、编译产物放在 `D:\Dev\cache\`。不在 C 盘建工作区或缓存。

### 3. §3 黄金规则 13 后面追加一段「派卡预授权」

> **派卡预授权：** 派卡提示里写明预授权的实现层事项，以及没写明但同时满足下面四条的事项，执行者可以自己决定，不必停下：卡外目录的最小扩展、增加已有的工作区依赖、与其他卡按清楚的边界并行、把落盘这类工作放到 `core-runtime` 等既有层次。前提是：(a) 不改契约 `.proto`；(b) 不加新的第三方包；(c) 不放宽任何阈值或验收；(d) 不涉及她是谁（规格、规律、性格、外观、声音、协议 p 的内容）。自己决定的事，在 PR 描述里逐条写明「决定 / 理由」，审查时把关。超出这四条，按第 13 条停下来问。

## 看板工具（`tools/status/`）

拆 PR 以后，看板不能因为第一个合并的 `n/m` PR 就把整张卡标成完成。

1. `build_status.py` 解析标题中的 `<任务号> n/m`：
   - 已合并的 PR 中，只要有一个 n = m，或者有一个不带编号的旧式标题，这张卡就算 done（仍按原规则处理 unverified 和部分交付）；
   - 只合并了 n < m 的 PR，算 partial，等待栏写「剩余 PR」。
2. `delivery.py`：没有 `REPORT.md` 的卡，部分交付只看 `BLOCKED.md` 和上面的 n/m 规则，不报错。
3. 测试：旧式标题、`1/4` 已合并、`4/4` 已合并、标题写错（例如 `5/4`、`0/3`）的情况都要覆盖。写错的标题不当作完成，在看板上标为异常。
4. `python -m pytest tools/status` 全部通过。
