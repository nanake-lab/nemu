## 问题及已核对证据

P5-36 要求 P5-25 真实内存结构与后继消息逐位往返，但本卡目录仅含 contracts、core-types 和生成目录。

在 main `3f8f98e5ac3cba2f2b4718ca242a5a0c226d0fbf`，`core-kernel/src/dynamics/types.rs:109` 的全部递推字段为 `pub(super)`，公开 getter 仅返回 θ、σ̂、τ̂、总权重、变化率/计数和零时长计数；`time.rs:14` 的四个时间字段同样私有，仅公开累计 running。现有构造器只有 genesis 和从 H 停机区间投影时间，没有恢复任意合法中间状态的接口。

因此在本卡范围内手造相似消息并验证其自身往返，不能证明真实状态往返。Debug 解析、复制 P5-25 源码、unsafe 布局访问或重新递推猜回字段，也不满足验收。

## 请求的最小接口

由 core-kernel 所属任务提供导出和恢复桥接，或在用户明确批准后把必要路径纳入 P5-36：

- 在 `core/crates/core-kernel/src/dynamics/` 内新增专用转换模块，并在 `mod.rs` 注册；保留状态字段封装。只有确需时才调整同目录的类型/时间方法。
- 导出真实 `DynamicsState` 的所有状态，使用 P5-36 生成的只读类型；不得新增另一套生产私有格式。
- 恢复接受新消息、已解析验证的规律参数/校准资源绑定，完整校验后一次性构造状态；失败返回错误，不能部分替换已有状态或初始化缺失值。

生产依赖方向保持 `core-kernel → core-types`。core-types 中的编解码和语义检查继续独立于核心执行和存储。

**本次不申请修改 `types.rs`、`time.rs`、`update.rs`、`duration.rs`、`detector.rs`、`bounds.rs`、`numeric.rs`、`lib.rs` 或 Cargo 清单。** `lib.rs:5` 已公开 dynamics，kernel 已依赖 core-types；现有 `pub(super)` 足够供新模块使用。若实施发现确需这些额外路径，另列具体原因，不把本请求视为整个 dynamics 目录的许可。

两个入口的责任如下（接口草案，尚未实现）：

- **导出：** 输入 `&DynamicsState` 和组装快照所必需的显式资源绑定，输出正式生成的完整估计器消息。只逐字段复制已保存位值并校验绑定，不运行 `stage`、不重新求 σ/τ/方差、不读取存储或实时时钟。单独的快照 revision/H 前缀等外层元数据不得从内存估计器猜造。
- **恢复：** 输入已解码的正式消息及调用方提供的已解析规律/校准资源绑定，返回 `Result<DynamicsState, 恢复错误>`。先完成有限性、布局、质量/计数、时间关系及完整参数/摘要检查，再一次性构造新状态；不接收旧 `DynamicsState` 作为补字段来源，也不访问原事件轨迹。资源内容自洽不等于可信来源，H 前缀和来源认证仍由外层负责。
- 恢复失败不得返回 genesis、部分恢复状态或修改既有实例。解码/恢复错误应与 C 的成长计算故障区分，不能据此擅自定义运行时降级或把损坏状态当成“无成长继续”；后继运行时按既定结构故障合同处理。
- `DynamicsFuses` 本身是每次 `stage` 的输入，不是当前 `DynamicsState` 的隐藏字段；恢复需核对快照声明的校准资源绑定，续算使用同一资源，不在本卡重新校准或改变 C 的签名。

### 为什么不能只使用现有接口

- `types.rs:174–196` 的 getter 缺少 reaction/square sums、variance、log sum/mass/mean、开放段、检测均值和正负累积量、末次事件/时间以及慢漂状态。`StagedDynamics::state/into_state`（83/86 行）只返回同一个封装类型，不提供这些字段的外部访问或重建。
- `DynamicsState::genesis`（132 行）会将计数、累积量和开放段初始化，不能恢复任意中间前缀。`RunningTime::from_history`（time.rs:24）需要完整停机区间，属于由 H 重新投影；它不是读取已保存四个时间量的恢复入口，`running_ns()` 也不能反推出其余三项。
- `core_types::WireMessage` 已能往返生成消息，但生成消息自身往返不能证明真实 DynamicsState 的映射完整。现有 P5-25 的 `identical`（tests.rs:45）使用 PartialEq + Debug 比较有限状态，现有前缀重放测试未经过序列化/恢复；本卡需增加直接逐字段位比较，不修改或重跑旧测试来冒充新验收。

### 真实状态逐位恢复的验证方案（本轮均未执行）

1. **来源必须是真实 C。** 用固定合成规律/事件调用现有 `genesis → stage → into_state` 取得每个前缀；覆盖四通道不同值、正/零时长、负对数时长、未结束段、停机累计、CUSUM 累积/重置、慢漂报警前后、ordinal 跳号与排除来源。明确断言各目标状态实际出现，避免全零状态掩盖漏字段。相邻浮点和次正规数只采用当前实现允许的合法构造，不放宽数值边界。
2. **必须真正经过字节。** 真实状态导出为生成消息，经现有 Canonical 编解码后恢复；另走 Protobuf → 生成消息 → 恢复路径。恢复只取得消息和已绑定资源，不能拿原状态或 H 前缀回填。复编码的规范字节须一致，但这只是其中一项断言。
3. **独立比对真实内存。** 在 kernel 内部测试直接对原状态、恢复状态的每个 f64 调用 `to_bits()`，对整数、schema 标记、Option、字符串及数组顺序逐项比较。覆盖 `DynamicsLaw`、ThetaValues、全部累积量/中间量、Detector、Run、RunningTime、事件与慢漂状态。采用无 `..` 的完整结构解构清单，使新增字段迫使测试同步；不能仅比较同一导出器的两份输出、摘要、PartialEq 或 Debug。
4. **恢复后继续算。** 在各个截断前缀分别恢复，使用完全相同的后缀事件和 law/fuses，与不中断路径逐步比较完整状态位值，以及 ThetaChange、signals、StepBounds（浮点也逐位比）。补无事件/排除来源的恒等、重复/倒序事件拒绝及计算故障不改变旧状态，避免只在恢复瞬间相同、下一步却不同。
5. **跨语言及反例。** 同一真实状态导出的字节经 Rust/Python/TypeScript 解码、复编码并回到 Rust 恢复，再做第 3 项检查。逐消息满足本卡 ≥3 合法/≥3 非法；额外篡改资源版本/完整参数/摘要、计数、非有限数、负质量、时间恒等式、开放段起点、长度/符号和截断/未知标签，确认错误由对应边界拒绝。任何重建失败都不能触碰此前有效的真实状态。
