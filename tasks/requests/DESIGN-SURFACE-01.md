## 为什么做

她现在只有两种表达：文字，加上舞台上的身体。有些话用这两种都说不好：要用户做选择的时候（「想和你打一局，现在／晚点／算了」），或者「给你看」比「跟你说」更好的时候（她找到的一张图、一个链接）。本卡设计她的第三种表达方式：**卡片**。

另外，用户决定把「驱动各家编程 agent（Codex、Antigravity/Gemini）的工作台」做成一个独立产品 **QO**（公开仓库 `nanake-lab/QO`，另有自己的卡）。Nemu 以后通过 QO 找助手。本卡只列出 **Nemu 对 QO 的要求**，QO 本身怎么做不在本卡范围内。

## 已定（不需要再讨论）

- **卡片可以弹到用户的其他窗口上面。** 用户 11-26 定「能」。默认打开，设置里有一个总开关可以关掉（由人定的东西都要可调）。什么时候不该打扰由她自己从经历里学，不预设频率上限，只保留防失控的保险丝（沿用 10-25 的主动性决定）。
- **用户对卡片的每一次回应，都是真实发生的事，要作为事件进 H。** 由已认证的桌面会话上传，不能由模型或 worker 代填。
- **卡片的种类和外框由程序固定，她只选种类、填内容。** 她不生成任意界面、HTML 或脚本。
- **沿用 `ApprovalRequestV2` 的规则：** 审批卡的 `title` 和 `detail` 由闸门生成，不由模型生成。审批卡就是现成的第一种卡片。
- **QO 里没有「她」。** 她的记忆、身份、权限，以及「派给谁」的决定，都留在 Echo 里。QO 只接活、报进度、交结果。她派出去的活，批不批由 Nemu 按 ADR 0047 决定，QO 不另立一套规矩。

## 要设计清楚的（每项给候选、取舍和推荐，逐条写「决定 / 理由」）

1. **卡片的最小种类。** 下面是**候选**，每一种都先用三问过一遍（能不能不加；一个人会怎么做；加了以后什么改不掉），能用文字说的就不加：
   - **选择卡：** 一句话加 2–4 个选项，可选附一个自由回答框；
   - **展示卡：** 一张图、一个链接或一个文件，附上来源和她的一句话；
   - **审批卡：** 现有的 `ApprovalRequestV2`，不改。

   每种都要写清：字段；哪些由她写，哪些由程序生成；长度和大小上限；三种语言怎么显示；过期时间。还要写清用户的几种反应：点了选项、自己回一句、关掉、一直没看到就过期。每种算不算她的经历，怎样记，不能编造「用户看到了」这类没观察到的事实。
2. **卡片出现在哪。** 至少比较这三处：
   - 舞台上她身边的气泡；
   - 面板里；
   - 压在其他窗口上面：置顶窗口，或者 Windows 系统通知。

   以下几点先在 Windows 11 上查证，写出处，查不到的标「须实测」：
   - 置顶窗口能不能盖住独占全屏的游戏，无边框全屏又如何；
   - Windows 限制后台程序抢焦点的规则：弹出时不能抢走用户正在打字的焦点；
   - 系统通知能不能带按钮，Electron 能做到哪一步；
   - 要不要遵守 Windows 的勿扰模式（专注助手），推荐默认值。

   给出默认行为，再说明总开关关掉以后她还能用哪些位置。
3. **她怎样发出一张卡片。** 写清整条链路：她提议 → 行动闸门（P5-14）→ outbox → 终端下行（#273）→ 桌面渲染 → 显示回执。
   - 按 ADR 0047，「显示一张卡片」属于哪一档；「压在其他窗口上」要不要单独的作用域；
   - 保险丝用现有的哪一个；
   - 同一张卡片重投、重启和断线时怎么办：已经显示过的不重复弹，结果不明时记 UNKNOWN。
4. **用户的回应怎样进 H。** 写清：
   - 新的负载类型（候选名 `CardResponse`）：哪些字段、怎样指回那张卡片的投递记录；
   - 从已认证桌面会话上传的入口；
   - 事件种类、属性规则表要加的那一行（来源 HUMAN_RESPONSE、外来）；
   - IRL 怎样理解它：选项本身是结构化的，不需要模型去猜；自由回答的文字照常走理解；
   - 卡片过期、被关掉时，记录的是哪个事实、由谁观察到。
5. **Nemu 对 QO 的要求清单。** 只写 Nemu 需要 QO 提供什么，交给 QO 的设计去满足，不规定 QO 怎么实现：
   - 派活时，Nemu 要带上哪些东西：用途、工作目录、权限范围、预算或档位、她给这件事起的名字；
   - Nemu 要收到哪些事件：状态、流式输出、待批准的操作（必须是原样载荷和摘要）、结果、用量；
   - 审批：她的活由谁批。要求是：QO 收到助手的审批请求后，交给创建这件活的客户端（也就是 Nemu），Nemu 按 ADR 0047 决定或转成审批卡给用户。QO 自己不能替 Nemu 的活做决定，QO 的界面最多只能看；
   - 结果怎样带着来源进 H：别人告诉她的，不能冒充她亲历的（ADR 0004 §6、S8）；
   - 断线、重启后怎样续上：事件可以按游标重放，同一件活不重复执行；
   - 安全：只在本机开放，要带令牌；她的核心目录不能成为助手的工作目录（ADR 0004 §6）。

   顺带写清现有的 `executors/codex-bridge` 以后怎么处理：改成 QO 的客户端，还是退役。
6. **契约影响。** 只列清单，不改 `.proto`：
   - 新增或后继的消息和字段，是否沿用 `@retains`；
   - 三端上传入口怎样拒收新的内部标签；
   - 桌面会话需要的新能力。
7. **后继实现卡。** 按 PR 拆小的规矩列出：契约卡、核心卡（卡片行动、回应入站、属性规则）、桌面卡（卡片渲染、置顶窗口、总开关）、Nemu 接 QO 的客户端卡。每张写目录、依赖和规模。都排在「第一次真的聊上」之后：要用到 HOST-01 2/2、P5-53、P6-01 2/2 打通的链路。
