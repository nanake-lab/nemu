## 为什么做

现在，核心认定「用户本人」靠的是 Windows 账户：HOST-01（#258）的 `nemu-core/src/authority.rs` 把当前 Windows 账户的 SID 做哈希，当作 `LocalUserBinding.principal_id`。P5-52（#260）的 `verify_birth_material` 又要求 genesis 的 `caretaker_id` 等于这个已认证的 principal_id。

这样做有两个错：
1. **身份被绑在一台电脑上。** 重装系统或换电脑，SID 就变了，她就认不出照料者。用户计划 12 月给她换一台新电脑。
2. **账户不等于人。** 任何人坐在这个已登录账户前打字，都会被当成用户本人。

## 已定（不需要再讨论）

- **u\* 的身份是用户持有的一把钥匙。** genesis 里登记的是这把钥匙（公钥或它的指纹），不是任何操作系统账户。
- **Windows 账户只是「用户授权过的一台设备」。** 新设备第一次使用时，用钥匙授权一次；以后日常聊天只靠设备，不用每次掏钥匙。
- **要紧的操作必须当场用钥匙证明是本人：** 诞生、ADR 0047 的管理类操作、不可撤回操作的批准。具体清单由本卡列出。
- **私钥永远不离开用户手里。** 核心只存公钥和授权记录。日志、H、证据里都不出现私钥和口令。
- **她「认得你」靠的是 H 里的共同经历，和钥匙无关。** 本卡只管谁有权做要紧的事。
- **排练阶段可以先沿用 Windows 账户。** #258 照常合并，但它的 SID 主体只用于排练，正式人生不得使用。实现落地后，排练也换成新机制。

## 要设计清楚的（每项给候选、取舍和推荐）

1. **钥匙放在哪里。** 至少比较：
   - Windows Hello / 平台通行密钥（passkey）；
   - 手机上的通行密钥（跨设备）；
   - USB 安全钥匙（FIDO2）；
   - 用口令保护的软件密钥文件。

   比较的维度：换电脑能不能继续用、丢了怎么办、要不要新增第三方依赖、许可证（应用代码不引入 GPL/AGPL）、Windows 自带 API 能做到多少。优先用 Windows 自带的能力。凡是需要新增第三方包的方案，列出包名、许可证和理由，实现卡里再批。
2. **备用钥匙与丢失恢复。** 诞生时至少登记两把钥匙：主钥匙和备用钥匙。写清楚丢一把时怎么办、两把都丢了怎么办。不设后门：两把都丢了，结果就是无法再做要紧的操作，聊天不受影响。
3. **设备授权。** 写清楚这几件事：新设备怎样授权；授权记录存在哪里，并把 #258 留下的问题「认证记录放在 H 外」一并定下；怎样撤销一台设备；换电脑的完整流程。用户 12 月换电脑是第一个真实场景，流程要能直接照着做。
4. **哪些操作要当场用钥匙。** 对照 ADR 0047 的权限类别和 v2.0 §§5.4、13、16 列一张表：每项写要不要钥匙、为什么。日常聊天、触摸这类不要；诞生、暂停或恢复成长、删除、导出、改权限档位、批准不可撤回的行动，按你的判断逐项写。
5. **身份号怎样从钥匙推出。** 包括 `LocalUserBinding.principal_id` 和 genesis `caretaker_id` 的推导方法；换钥匙或加备用钥匙时，身份号怎样保持不变。还要写清楚 genesis 的签名用什么算法、由哪把钥匙签。ADR 0049 只要求「签署人和已认证主体一致」，不改 0049。
6. **契约影响。** 列出需要新增或后继的消息和字段，标明是否沿用 `@retains`，三端上传入口怎样拒收新标签。本卡只列清单，不改 `.proto`。
7. **别的用户。** Nemu 是开源的，每个使用者都有自己的钥匙和自己的 Nemu。写清楚安装时怎样生成或登记钥匙。
8. **后继实现卡。** 按 PR 拆小的规矩，列出：契约卡、核心卡（替换 #258 的 SID 主体）、终端或桌面卡（授权和当场确认的界面）、迁移卡（排练从 SID 换到钥匙）。每张写目录、依赖、规模。
